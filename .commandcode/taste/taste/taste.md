# Taste
- Wants an AI assistant's claims to be backed by real actions: if the bot says it booked/scheduled something, it must actually write to the database via a real tool call — text-only role-play of completed actions is a bug. Confidence: 0.8
- Wants the bot to have complete, accurate company knowledge in its system prompt — mined from real company sources (site pages, docs), not generic or stale content. Confidence: 0.8
- Wants the bot to "handle responses well": graceful, fallback-able handling of upstream AI provider failures (non-JSON/HTML/WAF pages with 2xx status) instead of cryptic JSON.parse crashes or 500s. Confidence: 0.8
- Wants integrations fully linked to the real backend (e.g., Supabase): committed schema/migrations for every table the code depends on — in-memory fallbacks that silently lose data on restart are not acceptable. When the live DB is missing a table (user pasted `relation "projects" does not exist` from the Supabase SQL editor), the fix is a committed, self-contained, idempotent migration file (table + RLS + realtime + storage policies, safe to re-run) that the user runs themselves in the Supabase editor. Confidence: 0.9
- Wants user-facing surfaces (e.g., the website chat widget) upgraded to a modern, polished UI rather than left as dated hand-styled components. Confidence: 0.5
- Expects UI work to be mobile responsive as a first-class requirement — mobile layout (bottom-sheet/landscape behavior), safe-area insets for notched devices, adequate touch targets, and mobile-specific input handling (e.g., not disabling pinch-zoom, 16px inputs to avoid iOS focus-zoom). Confidence: 0.7
- Prefers the assistant to work from the actual live repo (points to GitHub URL) rather than relying on pasted transcript fragments. Confidence: 0.6
- Wants root-cause "why" explanations, not just surface fixes: when a symptom is reported (e.g., the bot replying "no listings available"), expects the cause to be traced through the actual code — comparing the failing query against the working app's query and the real schema/source of truth (e.g., the form that writes the data) — and explained clearly. Confidence: 0.6
- Prefers integrations to fail honestly rather than fabricate: no invented fallback listings to make the bot look functional — return empty results so the assistant reports truthfully. Confidence: 0.6
- Prefers loud, actionable diagnostics over silent failures: when fetched data doesn't match expectations (e.g., zero rows pass the status allow-list), log the actual values in use and suggest the concrete fix (e.g., the env var to override) instead of silently returning empty results. Confidence: 0.6
- Wants the admin to be able to actually communicate with website visitors through the chat box — a chat request should become a real two-way conversation (admin replies reach the visitor, visitor can keep messaging), not just a one-shot submission the admin can only flip status on. Confidence: 0.8
- Wants explicit read/unread semantics for incoming chat requests: a received request must not count as "read" by default or by status — it is marked read only when the admin actually opens/replies, unread badges track that flag, and a new visitor message re-flags it unread. Confidence: 0.7
- Prefers consolidating similar admin sections into a single unified view rather than proliferating tabs — explicitly asked to merge the Enquiries and Chat Requests tabs into one Inbox because "the tabs are getting much," with type/status filters replacing separate tabs. Confidence: 0.8
- Wants UI filter chip/badge counts to be consistent and truthful across rows: each count must reflect exactly what would be visible if that chip were clicked (honoring whichever other filter is active), never raw totals that disagree with the displayed list — reported as a bug when two "All" chips showed different numbers. Confidence: 0.7
- Prefers controlled numeric form inputs to render blank when the value is 0 rather than a literal "0" (so typing starts cleanly instead of appending to a visible zero), and to select-all on focus so typing overwrites existing values — a deliberate UX pattern applied consistently to every numeric field via a shared helper. Confidence: 0.6
- Wants user-facing actions to surface errors visibly (e.g., a rendered toast with the real error message) rather than failing silently — an action that stops with no on-screen feedback reads as "not working" (reported Create Project failure traced back to a toast state that was set but never rendered). Confidence: 0.5
- Prefers SQL migrations to be idempotent, self-contained, and convention-matching (mirrors existing repo migration style such as `chat_inquiries.sql`: `CREATE TABLE IF NOT EXISTS`, `DROP POLICY IF EXISTS`/recreate, realtime publication guard) so the user can run them safely in the Supabase SQL editor and re-run them. Confidence: 0.5
- Prefers to hand-review the full migration file (read it end-to-end) as a substitute for executing SQL when no Postgres is available locally, rather than shipping unverified SQL. Confidence: 0.5
- Prefers to keep harmless defensive/resilience code (e.g., the `map_link` retry-on-error in `handleSave`) even after the root cause is fixed, treating it as a safety net against partially-migrated databases. Confidence: 0.4
